## 3. File service — the delete and retry contract

`storage-own-cloud-faz1` proves "the same image attached twice is one object".
That result needs its distinctions drawn before it can be trusted:

- retrying the same upload produces one record;
- the same file attached to **two different notes** keeps two valid relations;
- removing it from one note does not break the other's image;
- a delete racing a retry must not resurrect a deleted file;
- another workspace uploading the same content must not share ownership or
  access.

If a shared object is ever used, the reference-counted delete behaviour has to
be written down explicitly. **Content equality is not permission to delete.**

## 7. Found during store acceptance, 13 September

Three defects that came out of the acceptance run but were deliberately **not**
folded into the store candidate, so the tested binary stays the tested binary.

**Unassigned orders can name an assignee.** `assigneeLabel` falls back to
matching a member by e-mail address. When a workspace carries a
`members.<uid>` entry with **no `email` field**, an order whose `assignedToUid`
and `assignedToEmail` are both empty matches that member on two empty strings,
and the card reads "Assigned to <that person>". Three helpers share the shape:
`OrdersScreen.kt:1967`, `OrderDetailScreen.kt:11426`, and the to-do variant at
`:11432`. Display only — nothing is written. Reproduced with an e-mail-less
member entry and confirmed to disappear once the entry carries one, which is the
shape the server's own writer always produces, so it needs legacy or
hand-written member data to fire. The fix is a guard against matching on a blank
e-mail; it is small, but it would invalidate an Android binary that has just
passed nineteen checks.

**The offline sentence promises a queue that does not exist.** Order edits go
through the `updateWebOrder` callable, and callables have no offline queue: an
edit made offline never reaches the server, reports "Could not update project.",
and is gone after a relaunch. Meanwhile the offline tooltip reads "Offline. You
can keep viewing saved data; new changes will wait for connection." Reading
offline is genuinely fine. Two ways out — stop promising the queue, or build one
for order edits — and the choice is a product decision, not a bug fix.

**Invoice Items rides on the customer permission.** `InvoiceItems` carries
`accessKey = "cardCustomer"`, so a member with *financial info* withheld still
sees the invoice lines and their total while the Financial Info card and
Estimate & Approval are correctly hidden. This is what the model says, on
purpose; recorded here so the decision is visible rather than assumed.
