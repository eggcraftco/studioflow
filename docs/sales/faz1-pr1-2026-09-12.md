## 2. What it deliberately does not do

It writes no order, creates no side document for any order, creates no catalog record, produces no stock, payment, notification, activation or retention event, and never re-stamps finance. It does not change the limit engine, the lifecycle engine or any existing callable. It adds no client code. The allowlist ships empty, so a deploy of this branch would open Sales for nobody.

## 3. The contract

### `getSalesCapability({ companyId })`
Never throws while Sales is closed; a client may call it on every load and should cache it for ten minutes, the way `getFeedbackPrompt` is cached.

```
{ ok, companyId,
  pilotEnabled,          // the flag names this workspace           (eligibility)
  visibility,            // "on" | "off" | "unset"                  (menu preference)
  showInMenu,            // pilotEnabled && visibility === "on" && permitted
  canOpenSales,          // permitted: memberAccess.orders and not workflow-only
  scope,                 // "workspace" or "assigned": the same scope Orders gives this member
  canManageVisibility,   // owner or admin
  canSeeMoney,           // memberAccess.financialInfo
  suggested,             // from the onboarding answers already stored; advisory only
  reason }               // flag_off | no_access | workspace_off | ok
```

### `setSalesVisibility({ companyId, visible })`
Owner or admin only, and only while the workspace is in the pilot. Writes `salesSettings/main` (`visibility`, `updatedAtMs`, `updatedByUid`). This is the only write in the PR.

### `listSalesRows({ companyId, limit?, cursor?, channel?, includeBespoke?, needsAttentionOnly? })`
Refuses a member without orders access and a workflow-only member. An assigned-only member is served the orders assigned to them: the scope reaches the query itself (`companyId` + `assignedToUid`), and when that composite index is missing the server reads the workspace page and filters before answering, so the answer is the same either way. Returns `{ ok, companyId, enabled, reason, rows, nextCursor, hasMore, financeVisible, scope, scanned }` with rows of exactly:

`orderId, kind, classificationSource, channel, externalOrderId, customerLabel, customerLabelWithheld, summary, itemCount, paymentState, deliveryState, workRequired, customerOwnedItem, cancelled, countsAsActiveOrder, needsAttention, attentionReasons, orderDateMs, createdAtMs, financeState, revenue, currency`

No contact detail, no address, no notes, no custom fields, no payment rows, no cost or profit figure. `revenue` and `currency` are `null` unless the finance stamp matches the current engine version **and** the member may see money; the row says which of the two it was through `financeState`.

### Which fields are the truth, and which are a view

| Thing | Source of truth | This PR |
|---|---|---|
| The order and its lines (`siparisler`) | the order document | read only |
| Money | the `finance` stamp written by `functions/finance/engine.js` | read only, never recomputed, never re-stamped |
| A Sales row | **derived at read time** from the order | computed per request, stored nowhere |
| `salesSettings/main.visibility` | the workspace's own choice | **implemented** |
| `salesOrders/{orderId}` (explicit classification, sale lines, `assignedToUid`, `orderDateMs`) | server-written side document | **schema and rules only — nothing writes it yet.** The row carries `assignedToUid`, so the rules can give an assigned-only member their own rows and nothing else, and its own `orderDateMs`, stamped from the order's `paymentDate`, then `createdAt`, then `createdAtMs`, with the source recorded: production carries `paymentDate` on 448 of 452 orders and `createdAtMs` on 12, so the list is never ordered by the order's creation stamp |
| `salesProducts/{productId}` (catalog) | server-written side document | **schema and rules only — nothing writes it yet** |
| A product-to-line link's state | computed from the link and the order's current lines | `functions/sales/links.js`, pure, tested |

### Link consistency, since the shipped iOS/Mac 1.3 rewrites whole orders

`functions/sales/links.js` fixes the rule now, before any writer exists: a link matches only by its recorded line id **and** an identical fingerprint (name, quantity, unit price). Array position never matters, and a name or a SKU never re-matches on its own. The states are `linked` (only this one may move stock), `changed`, `suggested` (one look-alike after the id was reminted — a proposal shown to a person, never adopted), `ambiguous`, `missing`, `orphaned` (the order was trashed or deleted). A restored order returns to `linked` only when the line is identical again.

## 6. Open risks

1. **Orders without `paymentDate` are invisible to the list.** The query orders by that field, and Firestore omits documents that lack it. Every creation path writes it today (`functions/feedback.js` relies on the same fact), but a very old or hand-written document might not. The later projection removes the risk by carrying its own timestamp; until then a workspace could have an order the Sales list never shows.
2. **Filters run after the page is read**, so a filtered page can return fewer rows than asked while `hasMore` is true. A client must keep paging rather than treat a short page as the end.
3. **The assigned scope depends on an index.** The list asks for `companyId` + `assignedToUid` + `paymentDate`, which is prepared in `firestore.indexes.json` but not published. Until it exists the server falls back to reading the workspace page and filtering, which is correct but reads rows that member may not see; it never returns them. Publishing the index removes the extra reads.
4. **Classification is honest but thin**: everything except a repair intake is `needs_review` until product links exist, so Faz 1 is "see and page the sales and channel orders", not a classified list.
5. **The demo-quota difference is real**: `countActiveOrders` counts a cancelled order as active, while the direction for Sales says it should not. The helper and its test record the difference; the limit engine is untouched.
6. **`getSalesCapability` does three reads per call** (flag, preference, workspace settings). Clients must cache it, or a list screen will read three documents per navigation.
7. **`appConfig/sales` does not exist in production.** Creating it is a live flag change and is deliberately not part of this PR.

## 7. Five-platform impact

Server only. No web, macOS, iOS or Android code changed, and nothing is visible on any platform until a client consumes the callables — that is PR 4 (web) and PR 5 (native). Evidence so far is emulator and unit level; device and store evidence do not apply to this PR and must not be claimed for it.

## 8. What a release decision would need

1. Merge this branch into the deploy branch normally, then deploy **three functions by name**: `getSalesCapability`, `setSalesVisibility`, `listSalesRows`. They are inert while no workspace is listed.
2. Publish `firestore.rules`. This is a whole-file rules release, so it needs the usual rules review; the change itself is three blocks plus six deny entries.
3. `firestore.indexes.json`: the four projection indexes may wait, but the assigned-scope index `(companyId, assignedToUid, paymentDate)` should go out with this PR — without it an assigned-only member's list falls back to reading the workspace page and filtering on the server. The workspace read uses the existing `(companyId, paymentDate)` index.
4. Opening a workspace is a one-document write to `appConfig/sales` afterwards, and closing it again is the same write reversed — no redeploy either way.

Rollback: revert the merge and redeploy the three names, or simply leave them unopened; the rules revert with the file. Nothing to migrate, because nothing was written.

## 9. Native minimum build for the write phases (plan, not code)

When Faz 2 starts writing stock, the write callables will take the client's build number and refuse below a threshold with a message that names the update. That check is a convenience, not a control: an old client can still call every server path, so each invariant — the reservation, the idempotency key, the link state — is enforced on the server whatever the caller says it is. The pilot is per workspace, so a workspace whose devices are behind simply does not get the write phase, and before any threshold is switched on the report has to say which workspaces it would block and what the upgrade path is. No silent blanket block.
