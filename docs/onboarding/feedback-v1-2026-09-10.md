# Feedback v1 — the first in-app feedback loop, built and previewed (10 September 2026, 20:10–21:45Z)

Branch `onboarding-feedback`, cut from the deploy branch at `493afa0d`. Nothing deployed, nothing published, no
production document touched; the flag `NIVADESK_FEEDBACK` is unset everywhere, so even a deploy of this code changes
nothing a user sees until the line is added. Evidence: `docs/onboarding/feedback-v1-2026-09-10-raw/screenshots/`
(nine PNGs rendered against the local emulator stack — dev server, Auth/Firestore/Functions emulators — with the
same code; the emulator data is synthetic: workspace "Feedback QA Studio", one order for "Ada Lovelace").

## 1. What a person sees, and when

| Moment | What appears | Where it comes from |
|---|---|---|
| The workspace's first **substantive** order exists (a named customer or money or line items or a shipment or a contact channel or a recorded payment — the same `SUBSTANTIVE_ORDER` rule the setup checklist uses; an opened-and-empty "New Order" shell and a brand-new workspace never qualify) | a small card in the bottom-left corner, no overlay, no timer: **"How is it going so far?"** — "Your first order is in. Two taps tell us what to fix next." — *Give feedback* / *Not now* (`01-invitation-on-orders.png`) | `getFeedbackPrompt`, asked by the web shell once per ten minutes per session and on page changes after that; a yes is kept for the session so navigating does not flicker it |
| *Give feedback* | the short form: **Overall** (Going well / It's okay / Struggling — the one required answer), **What is it about?** (Something isn't working / Something is missing / A suggestion — optional, one tap), **Tell us more** (optional, ≤ 2000 characters), one line saying only what is written plus the account e-mail is sent; *Send* / *Not now* (`02-form-empty.png`, `03-form-filled.png`) | `submitFeedback` |
| *Send* | **"Thank you — we read every note. If it needs a reply, we will write to the email on your account."** + *Close* (`04-sent.png`); the corner card is gone for good for this prompt | the campaign is marked answered in the person's state; `feedback_submitted` recorded |
| *Not now* (on the card or on the form opened from it) | the card disappears; it does not return for 30 days (messaging.js's dismissal cooldown); an ignored, unanswered card may return after 7 days (the `feedbackPromptMaxPer7d` cap read as a window) | `dismissFeedbackPrompt`; `feedback_prompt_dismissed` recorded |
| Any time, once the feature is on | account menu (avatar, top right) → **Send feedback** → the same form with the "Send feedback" title and *Cancel* (`05-account-menu-entry.png`, `06-manual-form.png`). Never held back by the prompt's cooldown, only by the abuse limits | `submitFeedback` with `trigger: "manual"` |

The two prompts the spec describes for later (§36 missing-expectation after two sessions, §37 non-activation after
24–48 h) are **not built**: both need activation data that can be trusted, and the funnel still runs the old
derivation until the v2.1 cutover package is approved. Recorded as a dependency in §5, not approximated.

## 2. Where the answer goes, and where it is read

- **`feedback/{id}`** (root collection, server-only in the rules): `companyId, uid, userEmail, workspaceName, source:
  "in_app", platform: "web", trigger, campaign, stage, feedbackType` (§41: `onboarding_effort` for a one-tap
  first-success answer, `bug_report` / `feature_request` / `general_feedback` from the kind), `kind, experience, text,
  category: "other", impact: null, status: "new", ownerUid, adminNote, page, language, createdAtMs, statusHistory`.
  Nothing else rides along — no customer, order, bank or address fields; the tests pin the field list.
- **`companies/{cid}/feedbackState/{uid}`** (server-only): what this person was shown and when, dismissals, a bounded
  submission history (a hash of the text, never the words), the campaigns already answered, and the lifecycle events
  `feedback_prompt_shown` / `feedback_prompt_dismissed` / `feedback_submitted` (the names `derive.js` lists as
  "the system's own records").
- **Reading it:** `/admin` → sidebar **Customer Feedback** (admin-only: a verified address in `SUPPORT_ADMIN_EMAILS`,
  the same gate as the activation funnel). Newest first; filters by status (§44) and type (§41); each row shows
  when, type and kind, experience, workspace, sender, the first line and the status; *Open* shows the full note,
  page/platform/language, the status select, an internal note, *Save*, and the status history
  (`07-admin-inbox-list.png`, `08-admin-inbox-detail.png`, `09-admin-status-changed.png`). No e-mail is sent to
  the person by any of this.

## 3. Server rules that hold (all tested)

- Identity and workspace: every user callable goes through `requireWorkspaceForBilling` (signed in, member of the
  workspace named in the call); a member of another workspace is refused with `permission-denied`; the inbox callables
  refuse anyone not on the admin list, unverified admin addresses included.
- Limits: experience must be one of three values, kind one of three, text ≤ 2000, page ≤ 200, client key ≤ 80;
  5 notes per hour and 20 per day per person per workspace (`resource-exhausted` beyond); a retry under the same client
  key inside 24 h and the same words inside 10 minutes return the earlier note's id instead of a second document.
- Prompt rules, from `lifecycle/messaging.js` unchanged: `feedback_prompt` at most once per 7 days, a dismissed prompt
  closed for 30 days, the in-app daily cap; plus this module's own two: no first success → no prompt, answered → never
  again. The manual entry bypasses all of the prompt rules.
- Flag: `NIVADESK_FEEDBACK=1` on the functions runtime. Off: `getFeedbackPrompt` answers `enabled:false` and the web
  shows neither the card nor the menu entry; `submitFeedback` / `dismissFeedbackPrompt` refuse with
  `failed-precondition`. The admin inbox is not behind the flag (admin-only regardless), so anything submitted can
  always be read.

## 5. Done, missing, and what going live takes

**Done (web + server):** invitation after the first real order; the form with the required one-tap answer and
optional kind and text; close/snooze and sent states; the always-available account-menu entry; server record path
with auth, limits, duplicate and abuse protection; events; the 7-day cap and cooldowns; the admin inbox with status
changes; rules; translations; tests — `functions/test/qa/feedback.test.js` (13 checks: flag off, empty workspace,
shell order, first success and the 7-day window, dismiss and the cooldown, submit + field list + never-again, retry
and double-click, manual entry vs cooldown, validation, the hourly limit, unauthorised access, the inbox) and
`feedback-rules.test.mjs` (20 checks on the emulator: nobody reads or writes either collection); full `npm test`
green (all qa suites); `tsc --noEmit` clean; the emulator preview above.

**Missing / not in this release:**
- Native apps (iPhone, Mac, Android): no feedback surface yet. Web only.
- §36 / §37 prompts (missing expectation, non-activation): blocked on trustworthy activation data (the v2.1 cutover
  package, kept separate); §35's "what made it difficult?" follow-up options and §38–§39 blocker/contextual help.
- Category and impact are stored (`other`, `null`) but not editable in the inbox; no owner assignment beyond
  "whoever last saved"; no filters by workspace or date; no export.
- The funnel (`getActivationFunnel`) does not yet read `feedbackState` events into `derive.js`.
- The admin hub's sidebar labels are plain English strings like every other entry there (existing pattern); every
  string inside the inbox and the user form goes through `t()`.
- Any reply to a person is manual, by e-mail, outside the product (by design for this release).

**Going live — the exact steps, each an approval:**
1. Merge `onboarding-feedback` into the deploy branch (normal merge; the branch carries the Stripe fix).
2. `firebase deploy --only firestore:rules` — the two new server-only blocks and the deny-list entries.
3. Deploy the six functions by name: `getFeedbackPrompt, dismissFeedbackPrompt, submitFeedback, listFeedback,
   getFeedbackDetail, updateFeedbackStatus`. Decision: add `NIVADESK_FEEDBACK=1` to `functions/.env` **before** this
   deploy (on from the first minute) or deploy without it and redeploy the six with the line later (the env is baked
   at deploy time; the runbook's shared-`.env` warning applies to any later deploy of these six).
4. Publish the web (a new Round through the publish repo): shell, account menu, form, admin inbox, translations, CSS.
5. Decision: who reads the inbox — today the three addresses in `SUPPORT_ADMIN_EMAILS`.
6. After the flip, the first real cards will go to workspaces that already have a substantive order and whose owner
   has never been asked — i.e. existing users see it on their next visit; if that should be new workspaces only, add
   a signup-date floor before the flip (one line in `promptEligibility`).
