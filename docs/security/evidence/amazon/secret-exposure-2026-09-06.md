## What the old token could do, and what it could not

It authenticated inbound carrier-tracking callbacks. Someone holding it could post forged tracking
updates for orders whose tracking numbers they knew, which can flip an order's dispatched or delivered
flags and send the customer a status message. It reads no customer data, authenticates to nothing
else, and is not a Google, Stripe or Apple credential.

## The revocation proof

Four synthetic requests to `https://track17webhook-ukbn4tcyca-nw.a.run.app`, 2026-09-06 19:58 UTC.
Neither token was printed by the commands; both were read into shell variables and used only inside
`curl`.

| Request | Answer | Meaning |
|---|---|---|
| **Old value** in `x-studioflow-token` | **401 `invalid_token`** | the exposed value no longer authenticates anything |
| New value as `?token=` in the URL | **401 `token_in_url`** | the form that wrote the old value into Cloud Run's request log is refused before the token is compared, so the new value cannot reach a log the same way |
| No token at all | 401 `invalid_token` | unchanged, still fails closed |
| **New value** in `x-studioflow-token` | **200** | the rotated value works |

The service's configuration was then read back: `TRACK17_WEBHOOK_TOKEN` is present **only** as a
Secret Manager mount, with no plain value. A `describe` of this service can no longer print it, which
is the exposure that started this.

## What is still true right now

The old value is **inert**: it authenticates nothing. Copies of it remain in this session's
transcript, in historical Cloud Run request logs, and in the configuration of the superseded revision
`track17webhook-00121-lub`. None of them is worth chasing now that the value is refused, and the old
revision is also the rollback target, so it stays.

**One step remains and it is the operator's**: 17TRACK still sends the old value, so real tracking
callbacks are being refused with 401 until its webhook configuration is changed to send the new value
in the `x-studioflow-token` header. Deliveries retry, and the hourly tracking sweep reads from the
carrier independently, so the cost is delay rather than lost updates.

## What the operator does, in order

Steps 1, 2 and 3 are done: the operator entered the new value in 17TRACK on 6 September at about
20:05 UTC.

**What is still unproved is the end of the chain.** No real delivery has arrived since the deploy —
the only requests in the log are the four synthetic ones — because 17TRACK only calls when a tracked
parcel actually moves. Until a real delivery answers 200, the rotation is proved on our side and
assumed on theirs. The next genuine callback is the proof, and it is being watched: a delivery that
answers 401 means 17TRACK is still sending the old value or still putting it in the URL, and the
answer is not to widen what we accept.

The original instructions, kept because they are the procedure if this happens again:

Read the new value once, from your own terminal, and put it into 17TRACK's webhook configuration **as
a header**, `x-studioflow-token`:

```
gcloud secrets versions access latest --secret=TRACK17_WEBHOOK_TOKEN
```

The assistant does not enter credentials into third-party forms. If 17TRACK cannot send a custom
header, say so: the URL form is refused now, and the answer is a different scheme rather than putting
a token back into a log.

## Why this is separate from the dependency soak

This is a **production change made during the soak window**, deliberately and with the operator's
instruction. The soak's clean result covers the 350 functions deployed in batches B0–B5.3 and the
absence of errors in that window; it must not be read as "nothing was changed in production on
6 September". When the deploy runs, `track17Webhook` gets a new revision for a security reason that
has nothing to do with the dependency remediation, and the soak record links here rather than
absorbing it.
