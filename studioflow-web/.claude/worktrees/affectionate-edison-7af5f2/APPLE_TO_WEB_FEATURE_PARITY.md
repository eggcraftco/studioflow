# Apple-to-Web Feature Parity Matrix

Created: 2026-05-07
Scope: StudioFlow Apple app, logged-in web portal, and Firebase Functions backend.
Task type: planning/documentation only. No implementation changes are included in this file.

This matrix uses the Apple Swift app as the source of truth and compares it with the current Next.js web portal and Firebase Functions. The repository was scanned dynamically for the current `EGGcraft/`, `studioflow-web/`, and `functions/` structure before drafting this document.

## Status Legend

- Done: Web behavior appears to match the Apple behavior for the core workflow.
- Partial: Web has a working implementation, but behavior, fields, gates, or UX are not fully at Apple parity.
- Missing: Web behavior was not found.
- Bug: Web implementation appears inconsistent with Apple behavior or backend permissions.
- Placeholder: UI or scaffold exists, but the behavior is intentionally not live or not complete.
- Not Applicable: The Apple behavior depends on native Apple platform APIs and should have a web-specific equivalent instead of a direct copy.

## Priority Legend

- P0 Critical: Must be fixed before web is treated as a safe app-equivalent workflow.
- P1 High: Important for near-term Apple parity or core studio operations.
- P2 Medium: Valuable polish or workflow completion after the core gaps.
- P3 Low: Nice-to-have, platform-specific, or acceptable later.

## 19. Recommended Implementation Batches

### Batch 0 - Safety, Permissions, and Billing State

Goal: make the web portal safe before expanding feature parity.

- Fix role helper mismatch so Workflow Only never gets full/finance edit UI.
- Add a compact parity test checklist for owner/admin/member/viewer/workflow across Orders, Settings, Team, Files, Dashboard, and Plan.
- Expand or explicitly map web plan entitlements to the Apple `StudioPlanEntitlements` model.
- Keep Stripe disabled by default (`STRIPE_BILLING_ENABLED=false`, `STRIPE_ALLOW_LIVE_BILLING=false`) until explicit launch.
- Test Stripe Checkout/Portal/Webhook with test prices only.
- Define server-verified StoreKit-to-Firebase billing update architecture before production StoreKit launch.
- Regression-test export access after expired/cancelled subscription fallback to Demo.

### Batch 1 - Core Order Detail Parity

Goal: close the highest-impact daily workflow gaps in the order detail page.

- Make Notes and custom fields editable where Apple allows them.
- Apply full Customer & Communication settings: channel labels, visibility, custom channels, and contact field parity.
- Audit Financial Info against Swift calculations and add missing custom expense/remaining rows or label controls.
- Add live Shipping & Tracking UI using the existing tracking backend functions.
- Verify Preview, Summary, Materials, Production Status, Priority/Risk, To Do, Client Files, and History all write history entries consistently.

### Batch 2 - Workspace Blocks and Card Profiles

Goal: make web layout customization predictable across Apple and web.

- Add/complete named Card Profiles UI if Apple profiles are official.
- Expose owner live sync and Stop Sync/Rejoin Shared Layout states clearly.
- QA app-compatible fields: `kartYerlesimi`, `sutunGenislikleri`, `kartYukseklikleri`, `kartRenkleri`, `phoneKartSirasi`, `visibility`.
- Verify mobile move up/down, desktop drag, resize, color, hide/show, and independent per-order layouts.
- Add field-level regression tests or fixtures before broad layout changes.

### Batch 3 - Schedule, To Do, Calendar, and Reminders

Goal: choose and implement the correct web equivalents for native reminder systems.

- Decide whether web reminders use browser push, email, backend push, ICS/VTODO only, or a combination.
- Align Schedule and To Do plan gates with Apple Lite/Pro/Team rules.
- QA schedule move/resize on desktop and mobile.
- Add Google/Microsoft calendar links if useful after `.ics` export is stable.
- Confirm Team-only To Do assignment is enforced in both UI and backend.

### Batch 4 - Client Files Web Equivalents

Goal: finish the web version of Client Files without pretending it is the native share sheet.

- Document or implement browser equivalents for Share Sheet inbox and Make Offline.
- Consider IndexedDB pending upload queue if offline web use is required.
- QA upload safety, max size, allowed types, delete/rename/use-as-preview, and storage cleanup errors.
- Keep Client Files cloud access Pro/Team only.

### Batch 5 - Settings, Dashboard, Quick Reply, and Navigation Polish

Goal: make the portal feel cohesive and app-compatible.

- Compare every Settings section field against `AyarlarView.swift` and fill missing low-risk fields.
- Localize remaining logged-in portal copy through `studioT` where practical.
- QA Dashboard widget visibility and financial calculations against Apple fixtures.
- Decide whether Files, Export, Plan, and Team belong in primary nav or Settings shortcuts.
- Keep Apple On-Device AI as app-only with clear web fallback copy.

### Batch 6 - Customers, Team, and Workspace Management

Goal: support multi-user/multi-workspace workflows from web.

- Add request-access by owner Company ID if web onboarding needs it.
- Add workspace switcher for users with multiple accessible workspaces.
- Decide whether to add manual add-by-UID/email or keep request-based flow.
- Add customer profile image upload if official.
- QA customer previous-name order sync and role restrictions.

### Batch 7 - Export, PDF, Backup, and Data Safety

Goal: prove users can always leave with their data.

- Validate app-compatible backup export/import round-trip with the Swift app.
- Compare web Order PDF, To Do PDF, and History PDF against Swift output.
- Confirm CSV columns and date/number formatting.
- Confirm delete/import scope and warnings match Apple expectations.
- Re-test export availability on Free/Demo and after subscription fallback.
